# Optional personal reservations and two-mode Stop

## Unified homepage reservations

When `task_queue.unified_queue` is enabled, use `queue_unified.py`, `queue_planner.py` and `queue_unified_ui.py` instead of the older whole-node workflow below. The homepage has separate machine and total-card selectors: choose a configured single node with 1–8 cards, or both nodes with 2, 4, 8 or 16 cards in total, split equally (1+1, 2+2, 4+4 or 8+8). A selected single node never falls back to the other node. Card IDs are chosen from available queue capacity, with up to four cards on each node kept in one four-card group. Manual start/finish does not execute or stop workloads. Duration is entered as whole hours plus a 0–59 minute dropdown. Normal jobs remain limited to 1–120 minutes; scheduled night jobs may be longer.

The machine selector also offers **single node, any available** (`auto`), which lets the queue choose either node with suitable capacity. The new enqueue payload uses `machine` (`auto`, an exact configured node key, or `dual`) and `cards` (total count). Storage and planner `cards` remain the per-node count for dual requests, preserving earlier reservations. Older clients without `machine` keep automatic single-node selection and the original `dual: true, cards: 8` meaning of sixteen total cards. Do not reinterpret existing reservations during an upgrade.

New reservations must start and finish within the period from submission to 09:00 on the next calendar day in `task_queue.timezone`. Persist that deadline with the reservation; queue delays and later claims cannot move its estimated end past the original deadline. The ten-minute release buffer is additional scheduling space, not requested use time. If waiting leaves too little time, retain a visible cancellable entry with an expired-window message instead of silently deleting it. Existing active/legacy reservations keep their original behavior; passing the estimate or deadline never stops a workload. Verify minute-only and mixed durations, the two-hour normal limit, timezone/midnight boundaries, and delayed claims.

Each resource offer has a persisted ten-minute claim window, capped by any earlier scheduling deadline. The server scheduler runs independently of open browsers. An unclaimed offer releases its allocation and moves the reservation back exactly one waiting position; it retains the original application timestamp. Simultaneous consecutive timeouts pass the next reservation as one block, so each timed-out reservation moves one position. If nobody follows it, it retains the last position. A new offer gets a fresh offer ID; claim requests must carry the displayed ID, rejecting stale clicks after reallocation. Restarting the proxy must not reset an existing offer's timer or queue order, and already active work is never postponed.

While the homepage remains open, send desktop reminders on allocation and after 2, 4, 6, 8 and 9 minutes, deduplicated within that offer. Show the remaining claim time and timeout count in the table. **Start use** acts directly on one click; cancellation and finishing retain confirmation dialogs. Verify the exact ten-minute boundary, one-position movement, restart persistence, simultaneous timeouts, stale claims, reminder cadence and the absence of a start-confirmation dialog.

Use this extension when the user requests personal task queues or individual Stop permissions. Reuse the existing [control proxy and mutual-TLS host agents](container-control.md). The default deployment wizard remains read-only. This implementation reserves whole nodes in FIFO order; it does not execute launch commands, allocate individual cards, or stop tasks merely because another user is waiting.

## Establish the ownership model

Confirm whether startup is manual or automated, and the unit of reservation, when unknown. This implementation supports manual startup and one active reservation per node. Do not deploy it as an automatic executable-job scheduler.

Users register an employee ID, display name and personal password, then join either node's queue directly. No administrator approval or preassigned container is required. Registration, start and end records work without a container. Names and optional container associations are self-declared; passwords protect account/task access but do not independently verify corporate identity or container ownership. Do not describe this model as verified container ownership. Enable employee-based association only when requested and the team uses a consistent employee-ID convention. This reuses monitored attribution clues, not shell-history inference or independent corporate authentication.

Without automatic matching, an active reservation may optionally be associated with a running container after the user explicitly confirms it is their own. This associates existing and later NPU processes of that container instance. Do not use a shared multi-user container. The association cannot be changed, and a container cannot belong to two unfinished reservations on the same node. A user with host SSH/root access can still start jobs outside the queue; the webpage cannot enforce exclusive hardware use against them. Personal registration does not modify the trusted process-name roster or bypass the automatic container guard.

## Automatic association by employee ID

For deployments that request it, set `task_queue.auto_match_employee: true` on the proxy and every host agent. Also set the host agent's `task_queue.process_url` to its existing process-exporter metrics URL and `task_queue.process_metric_prefix` to the matching prefix (for example `ascend_process_`). Install `queue_ownership.py` on hosts and `queue_auto.py` on the proxy, with the updated queue modules. The ownership reader uses the existing `container_guard.py` helpers even if automatic guarding is disabled; install that dependency without enabling the guard policy.

After **开始使用**, the active node reservation continuously matches current NPU containers to the account's stored employee ID. The page displays matched containers and removes the manual-binding action. A person with multiple matching containers controls all listed targets through the reservation. Stop shows each container and PID, then rechecks the exact target set on confirmation. Changes require a new confirmation. The host rechecks employee attribution before accepting and executing a personal Stop. Real administrator direct Stop retains its override.

Require a successful, complete process inventory no more than 30 seconds old, container metadata no more than 45 seconds old, live process identities, exact Docker membership, unchanged container start time and the same employee on every current NPU process in each target. Unknown, mixed or unverifiable ownership blocks the affected target; an explicit conflict blocks personal Stop until resolved. Unavailable inventory blocks the operation rather than treating it as empty. Matching never starts or stops a workload by itself. Containers without NPU jobs are not auto-associated.

All matched targets are listed before multi-container Stop. Track each host operation durably, leave cancellation pending until all outcomes are known, and retain the reservation if any target fails or matching work remains. Never retry signals blindly. With zero matches, ending/cancelling only completes the record; with remaining NPU work, **结束登记** offers process/container stopping and waits for verified success before releasing the slot. Registration remains self-declared and does not change the trusted name roster, guard or whitelist.

## Installation on an existing control deployment

Keep actual host paths in the workspace-required operator directory on the existing data volume. Preserve config, certificates, guard state, roster and administrator credentials. Back up changed files with neutral timestamped names. No new port is needed.

1. Install the updated `container_agent.py` and `queue_processes.py` on every host. The latter uses the existing `control_common.py` and `process_exporter.py` modules. Verify Linux `os.pidfd_open`, `signal.pidfd_send_signal`, `/proc` visibility, current Docker/NPU access and Python 3.9+.
2. Add `"task_queue":{"operations_dir":"/data/operator/monitor/data/task-queue-operations"}` to each agent's existing JSON. Create that directory mode `0700`, owned by the agent user. Add only that directory to the service's `ReadWritePaths` if `ProtectSystem=strict` is in use. Keep the mTLS listener and Docker permissions unchanged.
3. Install updated `control_proxy.py` plus `queue_http.py`, `queue_store.py`, `queue_ui.py`, `queue_metrics.py`, `queue_auto.py` and `queue_processes.py` on the central host, readable by its dedicated unprivileged service user. Retain existing runtime dependencies. Add `"task_queue":{"database":"/data/operator/monitor/data/task-queue/queue.db","metric_prefix":"ascend","timezone":"UTC"}` to the proxy JSON. Choose a valid IANA display timezone (for example `Asia/Shanghai`) for the deployment. Create the DB parent mode `0700`, owned by the proxy user; allow this parent in `ReadWritePaths` for SQLite's WAL sidecars. Keep `UMask=0077`. The proxy must not gain Docker socket access.
4. Apply `patch_dashboard.add_queue_panels(dashboard, node_names, prefix)` for homepage queue tables, or `add_queue_link()` for a link only. Homepage tables are inserted after the guard table, preserving existing panels. Add one Prometheus scrape job targeting the existing proxy's loopback port, `metrics_path: /a5-queue/metrics`, `scrape_interval: 5s`; validate with `promtool check config` before reloading Prometheus. The endpoint publishes only public queue fields, and an empty row per idle node. Verify the new target in addition to existing targets. Preserve data-source IDs, metric prefixes, titles, Stop links and guard links. Existing `/a5-control/confirm` links redirect to `/a5-queue/control`; keep `targetBlank:true` so Grafana's client router does not swallow the route.
5. Reload systemd only if its configuration changed, then restart changed services. Do not restart workloads, clear queue data or reset passwords. When upgrading the earlier grant-based queue, update the proxy's three queue modules and restart only the proxy. The database migrates its uniqueness index to permit multiple reservations without containers; legacy grant records are no longer consulted. Preserve existing users, sessions and reservations and take a consistent SQLite backup first. Check service health, the two separate queue sections, the dashboard link, anonymous viewing, real administrator identity, and every existing scrape target.
6. Generate the Windows access package as the final workflow step. Existing launchers continue to use the same proxy port; users need no new client dependency. Optional HTTPS and the local tunnel access the same server-side accounts and reservations, but browsers have separate sessions on different origins.

## User workflow

1. Open the dashboard's **任务排队 / 我的任务** link. Register an employee ID, name and personal password (10–128 characters), or sign in from any PC.
2. Enter a task description and **预计占用（小时）** in the desired server's queue section and select **加入队列**. Each server has a separate queue and start/end records. No personal password is preset. The requested duration is displayed for coordination only; expiry never automatically stops a task.
3. When first and the node has no active reservation, select **开始使用** and confirm. Launch the service yourself over SSH. This button only records occupancy; no container is required.
4. After finishing, select **结束登记**. In automatic mode it checks the current matching NPU jobs; in manual mode it checks the associated container, if any. The confirmation dialog offers **仅停止 NPU 进程** or **停止整个容器** when there are matched targets. It lists every affected target and warns that whole-container stopping interrupts all its services. After confirmation, retain occupancy until every stop succeeds and no matching work remains; then mark the task **已结束** and release the slot. Failure, remaining processes or an unknown result retains occupancy. With no matched target, end the record without sending a stop command. A bound container without NPU work can still be explicitly closed in manual-association mode.
5. For browser Stop in automatic mode, review the matched containers on the active task; no binding step is needed. In manual mode, first select **关联容器（可选）** and confirm your own container. **Stop** offers **仅停止 NPU 进程** (TERM, then KILL for remaining selected processes after five seconds) or **停止整个容器** (Docker stop with 30-second grace). The latter affects all container processes, including non-NPU services. Cancelling a waiting reservation never signals anything.
6. Only the submitting account or a real administrator can change a task, manually associate its container (when enabled) or stop its confirmed targets. Administrators can also use the dashboard Stop link directly. Personal users can follow that same link for their own associated active reservation. The guard/whitelist page still requires a real Grafana administrator.

Homepage tables show queue position, status, employee ID/name, task, application time, requested duration, actual start time and elapsed use. The associated container is shown on the task page. Elapsed use starts at **开始使用**, remains zero while waiting, and is computed from server time. Finished tasks leave the current homepage queue; the owner's recent history (and administrator history) keeps fixed start/end times and elapsed duration in the task page. Existing reservations without requested duration show a blank duration instead of an invented value.

## Security and failure behavior

Personal passwords use random salts and scrypt hashes in the private SQLite database. Session tokens are random, hashed in the database, HttpOnly and SameSite=Strict; HTTPS cookies are Secure. Do not ship databases, server key files, personal details or local passwords in packages. Password/name forms and API bodies must never enter logs.

Every mutation checks same origin and a custom header, and destructive confirmation tokens expire after 60 seconds and are consumed once. Ownership comes from the stored session account and reservation; administrator authority comes from Grafana. Client-supplied node names are restricted to the configured hosts. No browser-supplied command, hostname or Docker API path is executed.

The host compares full container ID, container start time, current NPU exporter membership, Docker membership and PID start ticks against the confirmation. Process mode opens PID handles and rechecks identity before any signal, avoiding numeric PID reuse. It does not kill non-NPU parent/supervisor processes, so an external launcher can respawn workers. In that case the reservation stays active and reports remaining processes; it does not repeatedly kill unconfirmed workers. A restarted container instance is not substituted for the original target.

Both modes record the actor, mode, target, selected PIDs and result without passwords or commands. Finishing with stop and cancellation both stay pending until the host's durable operation record confirms the result. After a service interruption, reconcile status without automatically repeating signals. Unknown results retain the reservation; review state before retrying. Persist the intended terminal state (`completed` for finishing, `cancelled` for cancellation) so recovery keeps the right outcome. An additive database migration gives legacy pending cancellations their original outcome. Finish-stop must be explicitly requested (`stop: true`) in both preview and confirmation, bound to the same one-use token and selected mode; old finish requests never gain implicit stop permission. Protect and back up the SQLite database and operation records with their containing directories.

## Validation

Run `test_queue*.py` (including automatic matching and multi-target HTTP tests) alongside the existing suite. The HTTP tests need aiohttp and fake both Grafana and host agents; they cover self-service registration without containers, independent node queues, optional association, migration, cross-account denial, forged roles, FIFO/occupancy, one-use confirmation, stale PIDs, CSRF, both Stop modes, finish-stop confirmation, pending/failed occupancy, recovery of completion state, and the old link redirect. The Linux PID-handle test signals only its own disposable CPU subprocess and verifies another subprocess survives. Do not test with business containers.

In a real browser verify: anonymous view, registration/login status, separate node queues, start/end records, automatic matching or optional manual association as configured, the actual dashboard link, and the Stop modal's two choices. Use intercepted fixture API responses for frontend task mutations, or an isolated test backend. Preview a real target if needed but do not confirm a production stop for testing. Do not confuse a skipped local aiohttp test with an executed HTTP test; use the server's isolated staging directory if it has the required dependency.
