# 预约与 Agent 任务的衔接

仅在用户授权 Agent 为指定任务自动操作预约时使用。创建或绑定用户指定的预约，确认预约编号、任务实际运行环境、启动方式、完成后释放或等待的偏好，以及拒绝续期时的停止方式；不凭预约自动推断这些信息。把执行计划、已启动任务的可验证标识、操作编号和处理进度保存在本地用户专有目录，供原会话恢复后读取；不得保存凭据到仓库。用户选择由 Agent 估计续期时，根据任务进度选择服务端支持的 10、20 或 30 分钟。

## 续接原会话

在 Codex 桌面端，可用 `automation_update` 工具创建绑定当前会话的 heartbeat；让它每分钟检查该预约、任务进度和截止时间，状态不变时静默，仅在需要操作、完成、失败或用户介入时继续处理。提示中指明预约编号和执行计划路径，要求恢复时先读取计划和当前实际状态，再行动，避免重复启动。完成或不再需要监控时，通过同一工具停用或删除本次创建的 heartbeat。创建成功不等于实际唤醒成功：未验证该环境确能恢复原会话之前，不承诺无人值守。不得声称服务端直接推送消息：这是 Codex 对预约接口的定时检查，受运行该 Codex 的电脑、应用、网络和调度条件限制，不能保证准时执行。

其他 Agent（包括 Claude）需要其运行环境提供能恢复原会话并定期执行的机制；先验证该机制，再承诺自动执行。没有可靠唤醒机制时，可以创建预约和记录计划，但必须告知用户不能保证无人值守，不要用新会话冒充唤醒原会话。

## 接口与状态

以下命令使用 `python <skill目录>/scripts/a5_client.py`。按已配置工号和姓名登录，服务端沿用现有预约权限；共同使用人也受服务端规则约束。

- `query` 获取本人预约、服务器时间和分配信息。事件仅用于提示，行动前必须重新查询当前状态。
- `events --job 预约编号 --after 游标` 获取持久化的 `ready` 和 `active` 状态变化；`--wait 秒数` 可选，范围 0–25。记录处理过的最大 `seq`；历史事件可能已经过期，不能单凭事件执行操作。已有预约在接入前就绪时，依靠 `query` 发现当前状态。
- 普通预约处于 `ready` 时，用最新 `offer_id` 执行 `action claim --job 预约编号 --offer-id 分配编号`。预约实际进入 `active` 后，按原计划在对应机器和容器启动任务，使用返回的卡位；恢复时先核对已记录的进程和任务状态，避免重复启动。夜间预约由现有夜间调度进入 `active`，不提前启动，也不对其重复领取。
- 普通预约到期且任务尚未完成时，按任务进度估计档位，执行 `action extend --job 预约编号 --minutes 10`（也可 20 或 30）。续期只能在到期后规定窗口内申请，受插空和夜间边界限制。若明确被拒绝，按用户预设安全停止该任务、保留已有输出或按任务支持的方式保存进度，并通知用户。不要停止其他任务或整个容器；无法可靠确认进程归属时停止自动操作并请求人工处理。夜间预约不支持此续期接口。
- 任务完成且用户选择释放时，先确认该任务已停止占用所有分配卡位，再执行 `action finish --job 预约编号`；若用户选择等待后续指令则保留预约，并继续关注到期规则。结束登记不等于停止进程。结果中的 `outcome` 和后续查询决定是否已释放；若显示等待清理，继续核实，不宣称立即释放。
- 每次 `action` 在发送前生成并保存操作编号。若网络或服务端故障导致结果未知，仅用 `action-retry 操作编号` 重试该操作，再核实当前状态；不要重新发起相同操作，也不要把未知结果当成成功或拒绝。

不要把排队状态或事件当作任务已启动、已完成的证明。断网、电脑离线、会话未被唤醒、任务运行位置失联或状态不明时，无法保证按时开始、续期或停止，恢复后应先核对预约、任务和之前的操作记录。
